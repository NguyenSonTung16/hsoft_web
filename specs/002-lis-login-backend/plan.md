# Implementation Plan: LIS Login Backend GraphQL API

**Branch**: `002-lis-login-backend` | **Date**: 2026-03-16 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/002-lis-login-backend/spec.md`

## Summary

Add a `login` module to the existing Apollo Server 5 / Express 5 / Oracle backend that
implements `loadFacilities`, `loadLabAreas`, and `submitLogin` GraphQL operations with full
Argon2id authentication, account lockout, atomic session + audit-log writes, and 7-day
sliding session tokens. The module follows the existing `entity` module pattern
(schema.ts / resolver.ts / service.ts). The only file outside the new module that requires
editing is `src/graphql/index.ts`.

## Technical Context

**Language/Version**: TypeScript 5.9 / Node.js LTS  
**Primary Dependencies**: Apollo Server 5.4, Express 5, oracledb 6.10, argon2 (new), graphql 16  
**Storage**: Oracle Database — tables LIS_FACILITY, LIS_LAB_AREA, LIS_USER_ACCOUNT,
LIS_USER_SCOPE, LIS_SESSION, LIS_LOGIN_ATTEMPT_LOG  
**Testing**: No automated test harness in scope; verification via Apollo Sandbox + manual DB inspection  
**Target Platform**: Node.js server (hoft-web-backend), CORS-locked to frontend at localhost:5173  
**Project Type**: GraphQL API service (web-service)  
**Performance Goals**: loadFacilities/loadLabAreas responses within 2 s; submitLogin within 3 s (SC-001, SC-003)  
**Constraints**: Argon2id-only password hashing; atomic session+log writes; no plaintext password at any layer  
**Scale/Scope**: Single-instance backend for login flow; uses existing per-operation Oracle connection open/close pattern

## Key Decisions

- **GraphQL operation names**: Use spec 002 names (`loadFacilities`, `loadLabAreas`,
  `submitLogin`). The 001 contract used `facilityOptions`/`labAreaOptions`/`login`;
  frontend `loginService.ts` adapter will need a follow-on update.
- **LoginResponse shape**: `LoginResponse { status: String!, message: String!, session: SessionState }` where `SessionState { sessionToken, reauthRequired, issuedAt, expiresAt, facilityId, labAreaId, workDate }` is a distinct GraphQL type. Error responses return `session: null`. This satisfies FR-004 (`SessionState` contract), FR-010 (response fields), and FR-011 (nested session bootstrap).
- **Session token**: `crypto.randomUUID()` — Node built-in, no extra package.
- **Connection pattern**: Existing per-operation open/close (`getConnection()`); no
  connection pool changes in scope.
- **FAILED_ATTEMPTS reset**: `UPDATE LIS_USER_ACCOUNT SET FAILED_ATTEMPTS=0, LAST_LOGIN_AT=SYSTIMESTAMP` is included **inside** the `autoCommit:false` transaction alongside `INSERT LIS_SESSION` and `INSERT LIS_LOGIN_ATTEMPT_LOG(submit_success)`. All three writes commit or roll back together (FR-020, Principle XXII).
- **Atomic write**: `autoCommit: false`; rollback called on any error inside the
  INSERT LIS_SESSION + INSERT LIS_LOGIN_ATTEMPT_LOG(submit_success) block.
- **Error-path audit logs**: Inserted with a fresh autoCommit connection (outside the
  atomic block) so failures are still recorded even if the session transaction rolls back.
- **Out of scope**: Admin unlock UI, user provisioning, automated test suite.
